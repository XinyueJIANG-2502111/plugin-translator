# Hover Translator

一个基于 Chrome Manifest V3 的悬停翻译扩展原型。扩展会在网页中识别鼠标悬停位置的文本，通过后台脚本请求翻译服务，并在光标附近显示用户所选目标语言的译文。

## 当前状态

项目已完成基本功能闭环，并完成了第一轮稳定性修正。目前核心权限、跨标签页状态同步、请求超时、缓存、去重、文本长度限制和高频事件节流已经落地，但第三方翻译服务、隐私合规及自动化测试仍需继续处理。

代码注释和界面源文件已统一为纯 ASCII，重要逻辑使用简短英文注释说明其解决的问题。README 继续使用中文，便于项目交接。

## 已实现功能

- 使用 Chrome Manifest V3。
- 在网页中监听鼠标悬停行为。
- 鼠标停留约 500 毫秒后发起翻译。
- 默认使用“段落模式”，读取当前元素的文本。
- 按住 `Ctrl` 临时切换到“单字/单词模式”。
- 用户可以在弹窗中分别选择源语言和目标语言。
- 源语言下拉框提供自动识别（`auto`）和英语（`en`），并已为后续语言预留扩展位置。
- 支持简体中文、繁体中文、日语、韩语、西班牙语、法语和德语。
- 在光标附近显示翻译浮窗。
- 根据视口空间调整浮窗方向、高度和水平位置。
- 鼠标进入浮窗时保持显示，移出后延迟隐藏。
- 扩展弹窗提供启用/停用开关。
- 使用 `chrome.storage.local` 保存开关状态、源语言和目标语言。
- 对 HTTP 错误、网络异常和响应解析失败提供基础提示。

## 项目结构

```text
plugin-translator/
├── manifest.json   # 扩展清单、权限和脚本注册
├── background.js   # 后台 Service Worker，负责请求翻译服务
├── content.js      # 文本识别、鼠标交互和翻译浮窗
├── popup.html      # 扩展开关界面
├── popup.js        # 开关状态读取、保存及消息通知
└── README.md       # 项目现状和后续工作说明
```

## 工作流程

1. `content.js` 被注入匹配的网页。
2. 用户将鼠标停留在包含文字的元素上。
3. 内容脚本按当前模式提取文本。
4. 内容脚本向 `background.js` 发送翻译消息。
5. 后台脚本请求 Google 翻译端点。
6. 翻译结果返回内容脚本并显示在浮窗中。
7. 用户可以通过扩展弹窗保存启用状态、源语言和目标语言。

## 问题跟踪

### P0：核心功能与可靠性

#### 1. 补充翻译服务的主机权限（已完成）

后台 Service Worker 会跨域请求 `https://translate.googleapis.com/`，但 `manifest.json` 没有声明相应的 `host_permissions`。在 Chrome 扩展环境中，这会导致请求不可靠或直接失败。

建议只申请实际需要的主机权限，不要扩大到所有远程服务。

#### 2. 让总开关在所有标签页同步（已完成）

目前修改开关后，`popup.js` 只通知当前活动标签页。其他已经打开的页面仍可能保留旧状态，直到刷新或重新加载内容脚本。

建议让内容脚本监听 `chrome.storage.onChanged`，以存储状态作为统一数据源。

#### 3. 评估并替换非正式翻译接口（待处理）

当前使用带 `client=gtx` 参数的 Google 翻译端点，没有 API Key、稳定性承诺、配额管理或备用方案，可能受到接口变更、限流和人机验证影响。

正式发布前应确定合规且稳定的翻译服务，并设计清晰的失败提示和降级方案。

### P1：性能、并发与数据规模

#### 4. 降低鼠标监听开销（已完成第一阶段）

当前在整个页面上监听高频 `mousemove`，并在事件中多次读取 `innerText`。复杂网页上可能产生明显性能开销。

建议减少事件内的 DOM 读取，增加节流，并尽可能延迟文本提取。

#### 5. 控制翻译请求数量（已完成第一阶段）

当前没有缓存、请求去重、取消机制或频率限制。在同一元素内移动、快速切换位置或网络较慢时，可能产生重复并发请求，旧结果也可能覆盖新结果。

建议加入：

- 相同文本结果缓存。
- 请求序号或 `AbortController`。
- 并发限制和请求节流。
- 对当前文本及鼠标位置进行二次校验。

#### 6. 限制文本长度并调整请求方式（部分完成）

段落模式直接读取 `e.target.innerText`。如果目标是大型容器或页面主体，可能抓取整页文本。当前又使用 GET 查询参数传输，长文本容易超过 URL 长度限制。

建议设置字符上限、优化段落识别，并根据正式翻译服务的接口要求使用适合长文本的请求方式。

### P2：交互与识别准确性

#### 7. 改进段落识别（已完成第一阶段）

当前“段落”实际是鼠标目标元素的全部 `innerText`，不一定对应语义段落，可能包含导航、按钮或整个容器。

建议优先识别 `p`、标题、列表项等文本块，并排除表单、脚本、样式、扩展自身 UI 和不适合翻译的交互元素。

#### 8. 改进单词边界规则（已完成第一阶段）

当前正则会把连续中文字符整体视为一个“单词”，中英文、数字和撇号也可能被合并。中文单字模式与英文单词模式应分别定义。

可以考虑使用 `Intl.Segmenter`，并为不支持的环境准备兼容方案。

#### 9. 修复 `Ctrl` 模式可能卡住的问题（已完成）

页面失焦、切换标签页或停用插件时可能收不到 `keyup`。此外，插件停用时会忽略按键释放事件，重新启用后可能仍停留在单词模式。

建议监听窗口失焦和页面可见性变化，并在停用或失焦时重置为段落模式。

#### 10. 增加请求超时（已完成）

当前网络请求没有超时控制。如果连接长期没有完成，浮窗可能一直显示“正在翻译”。

建议加入明确的超时时间、可理解的错误提示和有限次数的重试策略。

### P3：产品化和工程基础

#### 11. 提供语言设置（已完成第一阶段）

用户可以在扩展弹窗中分别选择源语言和目标语言。源语言当前提供自动识别和英语；目标语言提供简体中文、繁体中文、日语、韩语、西班牙语、法语和德语。选择会持久化并同步到所有已打开标签页。源语言使用独立的支持列表和校验函数，后续可以继续增加更多明确语言。

#### 12. 收紧网页访问范围并补充隐私说明

内容脚本当前匹配 `<all_urls>`，会在几乎所有可访问网页运行。悬停文本还会发送到第三方翻译服务。

正式发布前应：

- 评估是否可以缩小站点权限。
- 明确说明哪些文本会被发送到哪个服务。
- 避免处理密码框、编辑器和敏感表单。
- 准备隐私政策和商店权限说明。

#### 13. 建立基本开发流程

当前缺少版本控制、自动化测试和发布支持。建议逐步补充：

- 初始化 Git 仓库并设置忽略规则。
- 单元测试和浏览器端集成测试。
- ESLint、Prettier 等静态检查。
- 扩展图标和商店素材。
- 版本更新记录和打包流程。

#### 14. 将单词模式改为词典释义（待处理）

保留段落翻译，将按住 `Ctrl` 的单词模式改为查询词典，并显示词性、音标、释义和例句。实施前需要先确定支持的词典语言、释义语言、数据源、许可证和未命中时的回退行为。建议第一阶段只支持英文单词和英文释义，再考虑英汉或多语言词典。

## 建议实施顺序

1. 在 Chrome 中完成完整翻译链路和多标签页行为验证。
2. 确定正式翻译服务及隐私策略。
3. 评估 POST 或分段翻译，完善长文本支持。
4. 增加可主动取消网络请求的机制。
5. 添加自动化测试、版本控制、图标和发布文档。
6. 设计并实现词典模式。
7. 再扩展源语言设置、更多目标语言和其他产品功能。

## 当前结论

现有代码已经具备“悬停取词 → 后台翻译 → 页面浮窗展示”的完整链路，并处理了第一批权限、状态一致性、性能和并发问题。下一阶段最主要的风险是非正式第三方翻译接口、隐私合规和缺少真实浏览器自动化测试。在解决这些问题前，不建议直接面向大量用户发布。
