# Hover Translator

一个基于 Chrome Manifest V3 的悬停翻译扩展原型。扩展会在网页中识别鼠标悬停位置的文本，通过后台脚本请求翻译服务，并在光标附近显示用户所选目标语言的译文。

## 当前状态

当前版本为 `1.4.3`。项目已完成基本功能闭环和多轮稳定性修正，核心权限、跨标签页状态同步、语言设置、请求超时、缓存、去重、主动取消、文本长度限制和高频事件节流均已落地。正式翻译服务、隐私合规、全局限流及自动化测试仍需继续处理。

代码注释和界面源文件已统一为纯 ASCII，重要逻辑使用简短英文注释说明其解决的问题。README 继续使用中文，便于项目交接。

## 已实现功能

- 使用 Chrome Manifest V3。
- 在网页中监听鼠标悬停行为。
- 鼠标停留约 500 毫秒后发起翻译。
- 默认使用“段落模式”，优先读取光标命中的语义文本块。
- 按住 `Ctrl` 临时切换到“单字/单词模式”。
- 用户可以在弹窗中分别选择源语言和目标语言。
- 源语言下拉框提供自动识别（`auto`）和英语（`en`），并已为后续语言预留扩展位置。
- 支持英语、简体中文、繁体中文、日语、韩语、西班牙语、法语和德语作为目标语言。
- 在光标附近显示翻译浮窗。
- 根据视口空间调整浮窗方向、高度和水平位置。
- 鼠标进入浮窗时保持显示，移出后延迟隐藏。
- 扩展弹窗提供启用/停用开关。
- 使用 `chrome.storage.local` 保存开关状态、源语言和目标语言。
- 显式源语言与目标语言不能相同；旧版本遗留的冲突设置会自动修复。
- 光标只有真正命中文字范围时才会触发翻译。
- 鼠标移开或切换文本时会取消不再需要的翻译请求。
- 对 HTTP 错误、网络异常和响应解析失败提供基础提示。

## 项目结构

```text
plugin-translator/
├── manifest.json   # 扩展清单、权限和脚本注册
├── background.js   # 后台 Service Worker，负责请求翻译服务
├── content.js      # 文本识别、鼠标交互和翻译浮窗
├── popup.html      # 扩展开关界面
├── popup.js        # 设置读取、语言组合校验及状态保存
└── README.md       # 项目现状和后续工作说明
```

## 工作流程

1. `content.js` 被注入匹配的网页。
2. 用户将鼠标停留在包含文字的元素上。
3. 内容脚本按当前模式提取文本。
4. 内容脚本向 `background.js` 发送翻译消息。
5. 后台脚本请求 Google 翻译端点。
6. 翻译结果返回内容脚本并显示在浮窗中。
7. 用户可以通过扩展弹窗保存启用状态、源语言和目标语言。

## 问题跟踪

### P0：核心功能与可靠性

#### 1. 补充翻译服务的主机权限（已完成）

`manifest.json` 已为后台 Service Worker 声明 `https://translate.googleapis.com/*` 的 `host_permissions`，当前没有扩大到无关远程服务。

后续更换正式翻译服务时，需要同步更新并继续保持最小权限范围。

#### 2. 让总开关在所有标签页同步（已完成）

开关和语言设置以 `chrome.storage.local` 为统一数据源，所有已打开页面通过 `chrome.storage.onChanged` 接收更新。

扩展重新加载后，旧页面中的内容脚本上下文仍需通过刷新页面重新建立。

#### 3. 评估并替换非正式翻译接口（待处理）

当前使用带 `client=gtx` 参数的 Google 翻译端点，没有 API Key、稳定性承诺、配额管理或备用方案，可能受到接口变更、限流和人机验证影响。

正式发布前应确定合规且稳定的翻译服务，并设计清晰的失败提示和降级方案。

### P1：性能、并发与数据规模

#### 4. 降低鼠标监听开销（已完成第一阶段）

当前仍在整个页面监听 `mousemove`，但已通过 `requestAnimationFrame` 将处理合并到每个渲染帧一次，并把文本提取延迟到悬停计时完成后。复杂或频繁重排的网页仍可能需要进一步性能分析。

后续可根据实际性能数据评估更严格的节流或局部监听策略。

#### 5. 控制翻译请求数量（已完成第二阶段）

当前已实现相同文本结果缓存、相同请求合并、请求序号校验和主动取消。页面不再需要旧结果时会取消自己的订阅；共享请求失去全部使用者后，后台会通过 `AbortController` 中止实际网络请求。尚未实现全局频率限制或并发上限。

剩余工作：

- 并发限制和请求节流。

#### 6. 限制文本长度并调整请求方式（部分完成）

当前已优先选择语义文本块、排除页面根容器，并将单次文本限制为 1500 个字符。翻译请求仍使用 GET 查询参数，编码后的长文本仍可能接近 URL 长度限制。

后续应根据正式翻译服务的接口要求评估 POST、分段翻译或更严格的长度限制。

### P2：交互与识别准确性

#### 7. 改进段落识别（已完成第一阶段）

当前会先确认光标真正命中文本范围，再优先选择 `p`、标题、列表项、表格单元等语义文本块，并排除表单、可编辑区域、页面根容器和扩展自身 UI。

复杂网页中的自定义组件仍可能需要增加更细致的文本块规则。

#### 8. 改进单词边界规则（已完成第一阶段）

当前优先使用 `Intl.Segmenter` 识别单词边界，并使用支持 Unicode 字母、数字和撇号的回退逻辑。不支持 `Intl.Segmenter` 的环境中，连续中文字符仍可能被回退逻辑视为一个整体。

如果后续增加更多显式源语言，应按语言补充更精确的回退规则。

#### 9. 修复 `Ctrl` 模式可能卡住的问题（已完成）

页面失焦、切换标签页、页面隐藏或停用插件时，内容脚本会主动重置为段落模式，避免因未收到 `keyup` 而停留在单词模式。

该项已完成，后续只需在新增快捷键状态时沿用相同的重置策略。

#### 10. 增加请求超时（已完成）

后台网络请求设置了 10 秒超时，内容脚本消息设置了 12 秒兜底，避免浮窗永久停留在 `Translating...`。

当前没有自动重试；是否增加重试应结合正式翻译服务的错误类型和限流规则决定。

### P3：产品化和工程基础

#### 11. 提供语言设置（已完成第二阶段）

用户可以在扩展弹窗中分别选择源语言和目标语言。源语言当前提供自动识别和英语；目标语言提供英语、简体中文、繁体中文、日语、韩语、西班牙语、法语和德语。选择会持久化并同步到所有已打开标签页。显式源语言和目标语言不能相同，界面、内容脚本和后台均有校验，旧冲突设置会自动迁移。后续可以继续增加更多明确语言。

#### 12. 收紧网页访问范围并补充隐私说明

内容脚本当前匹配 `<all_urls>`，会在几乎所有可访问网页运行。悬停文本还会发送到第三方翻译服务。

正式发布前应：

- 评估是否可以缩小站点权限。
- 明确说明哪些文本会被发送到哪个服务。
- 避免处理密码框、编辑器和敏感表单。
- 准备隐私政策和商店权限说明。

#### 13. 建立基本开发流程

当前缺少版本控制、自动化测试和发布支持。建议逐步补充：

- 初始化 Git 仓库并设置忽略规则。
- 单元测试和浏览器端集成测试。
- ESLint、Prettier 等静态检查。
- 扩展图标和商店素材。
- 版本更新记录和打包流程。

#### 14. 将单词模式改为词典释义（待处理）

保留段落翻译，将按住 `Ctrl` 的单词模式改为查询词典，并显示词性、音标、释义和例句。实施前需要先确定支持的词典语言、释义语言、数据源、许可证和未命中时的回退行为。建议第一阶段只支持英文单词和英文释义，再考虑英汉或多语言词典。

## 建议实施顺序

1. 继续验证不同网站、多标签页和异常网络条件下的行为。
2. 确定正式翻译服务及隐私策略。
3. 评估 POST 或分段翻译，完善长文本支持。
4. 评估是否需要全局并发限制和请求节流。
5. 添加自动化测试、版本控制、图标和发布文档。
6. 设计并实现词典模式。
7. 再扩展源语言设置、更多目标语言和其他产品功能。

## 当前结论

现有代码已经具备“悬停取词 → 后台翻译 → 页面浮窗展示”的完整链路，并处理了核心权限、状态一致性、文本命中、语言组合、超时、缓存、去重和请求取消问题。下一阶段最主要的风险是非正式第三方翻译接口、隐私合规、缺少全局限流以及缺少真实浏览器自动化测试。在解决这些问题前，不建议直接面向大量用户发布。
